# 004 — Delivery: CI, Docker, observability, docs

The final pass. No product behaviour changes; everything here is about getting
002 and 003 running somewhere other than a laptop, and knowing what it does once
it is there.

Five areas, in the order they are built (each is useful without the next):

1. **§1 CI** — tests on every pull request and every push to `main`.
2. **§2 Docker** — images for both apps, one root `.env`, ports 3400/3401.
3. **§3 nginx** — one host, `strongroom.shamko.me`, API under `/api/v1`.
4. **§4 Sentry** — errors, traces and logs for both apps in one project.
5. **§5 PostHog** — product events only, EU region.
6. **§6 README** — the deliverable the exercise actually asks for.

---

## §1 CI

GitHub Actions, `.github/workflows/ci.yml`, triggered on `pull_request` and on
`push` to `main`.

### §1.1 Jobs

| Job | Does |
|---|---|
| `check` | install, build `@dataroom/contracts`, typecheck every workspace, Prisma validate |
| `test` | Postgres 16 service, `prisma migrate deploy`, the full Vitest suite (unit + integration) |
| `e2e` | build both apps, boot them against the CI Postgres with local storage/mailer adapters, run Playwright |

`test` and `e2e` both need a real database — the integration suite is the main
guard on access control (002 §12), so CI running it against a real Postgres is
the point, not an optimization.

### §1.2 Rules

- Node 22, pnpm 10, both pinned; pnpm store cached on the lockfile hash.
- `e2e` uses the built images' own defaults: no Supabase, no Resend, no Google —
  the fallback adapters (002 §10.1, §9) make a credential-free run a real run.
- A failing job fails the PR. Nothing is `continue-on-error`.

## §2 Docker

### §2.1 What is containerized

`apps/web` and `apps/api` only. **Postgres is not** — deployment uses Supabase,
and the `docker-compose.yml` database from 002 stays a local-development
convenience, not part of the shipped stack.

### §2.2 One `.env`, at the repository root

A single `.env` at the monorepo root is the source of truth for all three
consumers:

- `apps/api` at runtime, loaded through `dotenv` pointed at the repo root;
- `apps/web` at build and runtime, same file;
- `docker compose --env-file .env`.

No per-app `.env` files in production. The apps must therefore resolve the root
`.env` explicitly rather than relying on the process's working directory.

### §2.3 Build-time versus run-time variables

This distinction is the one that breaks deployments, so it is stated plainly.

- **Next.js bakes `NEXT_PUBLIC_*` into the bundle at build time.** They must be
  passed as `ARG` to `docker build`, not only as runtime `environment`.
- Everything the API reads (`DATABASE_URL`, `JWT_SECRET`, Supabase, Resend,
  Google, Sentry DSN) is **run-time** and must not be baked into an image.

Each Dockerfile therefore declares `ARG ENV` plus the build-time variables it
genuinely needs, and nothing else.

| Variable | Consumer | Build | Run |
|---|---|---|---|
| `ENV` | both | ✅ | ✅ |
| `NEXT_PUBLIC_API_URL` | web | ✅ | — |
| `NEXT_PUBLIC_SENTRY_DSN`, `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST` | web | ✅ | — |
| `DATABASE_URL`, `JWT_SECRET`, `WEB_URL`, `API_PUBLIC_URL` | api | — | ✅ |
| `SUPABASE_*`, `RESEND_*`, `GOOGLE_*` | api | — | ✅ |
| `SENTRY_DSN`, `SENTRY_ENVIRONMENT` | api | — | ✅ |

### §2.4 Ports

- web listens on **3400**
- api listens on **3401**

Both are published on the host loopback; nginx is the only thing that talks to
them.

### §2.5 Images

Multi-stage, `node:22-alpine`, non-root user, production dependencies only in
the final stage. The API stage carries the Prisma schema and runs
`prisma migrate deploy` on start before booting, so a deploy applies its own
migrations.

## §3 nginx

One server block for `strongroom.shamko.me`, to be pasted into a system nginx
that already handles TLS.

- `/api/v1/` → `127.0.0.1:3401`
- `/` → `127.0.0.1:3400`

Because both live on one origin, the browser calls the API at the **relative**
path `/api/v1`. That removes CORS from production entirely and makes the session
cookie same-origin. `NEXT_PUBLIC_API_URL` is therefore `/api/v1` in production
and an absolute `http://localhost:3001/api/v1` in local development, where the
two apps really are different origins.

Uploads go straight to storage from the browser (002 §7), so nginx never carries
file bodies. `client_max_body_size` still needs raising for the local-storage
fallback path, which does proxy bytes.

## §4 Sentry

**One project, both apps**, distinguished by tag rather than by project — the
useful question during an incident is "what broke in this deployment", and a
single project keeps a frontend error and the API error that caused it side by
side.

- `service` tag: `web` | `api`.
- `environment`: from `SENTRY_ENVIRONMENT`.
- **Errors**: the API reports through the existing `DomainExceptionFilter`
  (002 §4.2), and only for `INTERNAL` — a 404 or a `NAME_CONFLICT` is the product
  working, not an incident. The web reports through the App Router error hooks.
- **Traces**: sampled at 10% in production, 100% elsewhere.
- **Logs**: forwarded from the API's Nest logger.
- Absent DSN ⇒ Sentry is inert. No crashes, no noise, no special-casing at call
  sites.

### §4.1 What must never reach Sentry

Node names, file names, folder paths, share tokens and email addresses are
diligence-sensitive. `beforeSend` strips share tokens from URLs and drops
request bodies. The user context is the account id only — never the email.

## §5 PostHog

EU cloud (`https://eu.i.posthog.com`). **Product events and identification
only**: session recording, heatmaps and autocapture are all disabled explicitly,
not left at their defaults.

- `identify` uses the account's **email** as the distinct id, per the owner's
  instruction, with `name` as the only other property.
- Events are named `object_verb` and carry ids and counts, never names or paths:

| Event | Properties |
|---|---|
| `dataroom_created` | `data_room_id` |
| `folder_created` | `data_room_id` |
| `file_uploaded` | `data_room_id`, `size_bytes`, `mime_type` |
| `file_previewed` | `data_room_id`, `mime_type` |
| `node_deleted` | `type` |
| `node_restored` | `type` |
| `share_link_created` | `node_type` |
| `share_people_invited` | `node_type`, `count` |
| `share_revoked` | `kind` (`link` \| `grant`) |
| `search_performed` | `has_query`, `filter_count` |
| `trash_emptied` | `entry_count` |

Absent key ⇒ inert, exactly like Sentry.

## §6 README

The exercise names the README as a deliverable, so it is specified rather than
improvised. It must contain:

1. Design decisions.
2. **Two setup paths, both complete**: local with pnpm and no cloud
   dependencies at all (local Postgres, local disk storage, in-memory mailer),
   and production with Docker + nginx.
3. A data model / ERD.
4. A "How it scales" section answering the three questions asked:
   subtree size and item count; what changes at 100,000 files; how sharing
   extends to per-user roles without remodeling.
5. A note on where and how AI was used.
6. Hosted URLs.

## §7 Testing

| Area | How |
|---|---|
| §1 | The workflow running green on the PR that introduces it |
| §2.3 | A test asserting the root `.env` resolver finds the file from either app's working directory |
| §4, §5 | Unit tests that both adapters are inert without credentials and never receive names, paths or tokens |
| §3, §6 | Reviewed, not tested — an nginx file and prose have no runtime behaviour here |

## §8 Decisions

| Decision | Why |
|---|---|
| One Sentry project, `service` tag | An incident spans both apps; two projects would split the story in half |
| Only `INTERNAL` is reported | Expected 4xx responses are the product working; alerting on them trains people to ignore alerts |
| PostHog identified by email | The owner's explicit instruction; it makes the funnel legible without a lookup |
| No names or paths in telemetry | Document names *are* the confidential material in a diligence tool |
| Relative `NEXT_PUBLIC_API_URL` in production | One origin removes CORS and keeps the session cookie same-origin |
| Postgres not containerized for production | Deployment uses Supabase; shipping a second database would invite drift |
| `migrate deploy` on API start | A deploy that needs a manual migration step is a deploy that eventually forgets it |
