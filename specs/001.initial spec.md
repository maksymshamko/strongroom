# 001 — Initial spec: Data Room MVP

## 1. Overview

A virtual data room: users create data rooms, organize files/folders inside them, and share a data room, a folder, or a single file — either via a public link or with specific people by email. Built as a due-diligence tool, so the tone is professional/trustworthy, not playful, and deletion/sharing edge cases need to fail safe (warn before destructive actions, never silent data loss).

## 2. Scope decisions (locked)

- Auth: Google OAuth + email/password. A demo user is seeded on first boot so email/password login works without building a signup UI.
- **DataRoom is a Node**, not a separate table. `type: DATAROOM` is the tree root (`parentId = null`). This unifies sharing — a data room, folder, or file are all just a `Node`, so `Share.nodeId` covers all three with no separate polymorphic path.
- Folder/file size and item counts: **incremental**, updated on the ancestor chain within the same transaction as the write (upload, delete, move). Not computed lazily.
- Sharing by email to a not-yet-registered user: grant is stored by email; on account creation, pending grants matching that email are linked to the new `userId`.
- Search and filtering: by name, type (folder/file), size, created/updated date, mimetype.
- Name conflicts (upload, rename, and move all share one resolution mechanism): a dialog offers keep-both (auto-suffix), add-as-new-version, or replace. Full semantics per trigger in §4.3a.
- In-app PDF viewer (not just download).
- Uploads go directly from the browser to Supabase Storage via a signed URL (not proxied through the API server) — lower latency, real per-file progress, no server-side bandwidth bottleneck. Signed URLs are scoped to a single object key, `content-type: application/pdf`, and a short expiry; the bucket additionally enforces max file size and allowed mimetypes. After the client reports upload completion, the backend verifies the object's actual size/content-type against storage before writing the `FileVersion` row — the client's claim is never trusted on its own.
- Email via Resend, for share-invite notifications only (no password reset — not needed since email/password accounts don't have self-serve signup, only the seeded demo user and any accounts a user sets a password on themselves).
- Access control: a data room and everything under it is visible only to its owner, plus anyone holding an active (non-revoked) `Share` on it or an ancestor node. Every read/write endpoint checks this before returning data — default-deny, not default-allow.
- Folder listing is paginated (cursor-based, not offset) from the start, with indexes on `(parentId, type, name)` and `(dataRoomId)`. Not built purely to demonstrate it — this is what the README's 100k-files answer describes, so it needs to actually be true.
- Explicitly **out of scope**, documented only: real-time invalidation for a user actively viewing a node that gets deleted by someone else mid-session (next request 404s cleanly instead).

## 3. Data model

```
User
  id, email, name
  passwordHash    -- nullable; null if the account was created via Google only
  googleId        -- nullable

Node                          -- folders, files, AND data room roots
  id, parentId (nullable, null only for type=DATAROOM)
  type: DATAROOM | FOLDER | FILE
  name
  path            -- ltree, materialized ancestor path
  size            -- bytes; for FOLDER/DATAROOM, sum of subtree; for FILE, latest version's size
  itemCount       -- for FOLDER/DATAROOM only
  ownerId
  createdAt, updatedAt, deletedAt

FileVersion                   -- only for type=FILE nodes
  id, nodeId FK
  storageKey                  -- UUID object key in Supabase Storage, never the filename
  size, mimeType, checksum
  versionNumber
  createdAt, createdBy

Share
  id, nodeId FK                -- the shared node: a DATAROOM, FOLDER, or FILE
  mode: PUBLIC_LINK | PERMISSIONED
  token                        -- for PUBLIC_LINK
  createdBy
  revokedAt

ShareGrant                     -- only for PERMISSIONED shares
  id, shareId FK
  email
  userId FK nullable           -- null until a matching account exists
  role: VIEWER                 -- enum leaves room for EDITOR later
  acceptedAt

ShareAccessLog
  id, shareId FK
  viewerUserId FK nullable
  anonId                        -- cookie/session id for anonymous viewers
  viewedAt
```

Node identity (name, parent, permissions, shares) is separate from file content (`FileVersion`). Sharing a file always resolves to "this identity, latest version" — a new version doesn't require re-sharing.

## 4. User flows

### 4.1 Auth and onboarding
1. Unauthenticated visitor → sign in with Google or email/password. No self-serve signup form for email/password; demo user is seeded.
2. On first authenticated visit for a given account: check for `ShareGrant` rows matching the account's email with `userId = null` → link them to the new `userId` → show a "shared with you" section alongside the (empty) data room list, so nothing shared before signup is lost.
3. Returning user with no data rooms yet → prompt to create the first one. Returning user with data rooms → dashboard listing them.

### 4.2 Data room lifecycle
4. Create data room → name only at creation. User can own unlimited data rooms.
5. Inside a data room with no content → drag-and-drop upload area and "create folder" both offered as empty-state actions.
6. Data room has a settings surface: rename, delete, share — same actions as any node, since it's a `Node`.

### 4.3 Folder and file operations
7. Browse a data room/folder: breadcrumb navigation, grid/list toggle.
8. Upload: multi-file, drag-and-drop, per-file progress (browser uploads directly to a signed Supabase Storage URL, so progress comes from the upload's own progress events).
9. Create a folder, from within any data room or folder view (not only the empty-state) — folders nest inside folders to any depth.
10. Rename a file/folder → conflict check against siblings in the same parent.
11. Move a file to another folder → conflict check against siblings in the destination.
12. Click a file → opens it. PDF renders in an in-app viewer. From the open view, share is offered directly (not only from the browser context menu).
13. Delete a node:
    - Not shared → confirmation dialog naming what will be deleted (counts for folders).
    - Shared with anyone (any active, non-revoked `Share`) → confirmation dialog additionally warns that shared access will be removed.
    - Deleting a file: cascade-deletes all its `FileVersion` rows, including the objects in Supabase Storage.
    - Deleting a folder or data room: cascades to the full subtree (nodes, their versions, their shares) — DB cascade plus a storage-cleanup pass for every `FileVersion.storageKey` under the subtree.
14. On file upload/node move/rename/delete update parent nodes update time

### 4.3a Name conflict resolution
Applies uniformly to upload, rename, and move whenever the operation would result in two `FILE` nodes sharing the same name in the same parent. One dialog, three options, same component regardless of trigger:

- **Keep both** — auto-suffix (" (1)", " (2)", ...). Upload: a new node is created with the suffixed name. Rename/move: the existing node (A) simply takes the suffixed name — no merge, no deletion.
- **Add as new version** — incoming content becomes a new `FileVersion` on the existing conflicting node (B). Rename/move: node A's current content is copied in as B's new version, then A is deleted — A's own prior version history is discarded, not preserved or merged.
- **Replace** — B's entire version history is deleted (DB rows and Supabase Storage objects), and the incoming content becomes its new version 1. Rename/move: A is deleted the same way, once its content has transplanted.

Any path that deletes a node's version history triggers the same storage-cleanup pass used for node deletion (§4.3 item 13) — no orphaned objects in Supabase Storage.

### 4.4 Sharing
15. Share dialog (from data room, folder, or file) offers two tabs: public link, or specific people by email.
16. Public link: anyone with the link gets read-only access to the item and everything nested under it. View is logged to `ShareAccessLog` (anonymous or authenticated viewer).
17. Permissioned: add by email. If the email matches an existing user, access is immediate. If not, the grant is stored pending and linked automatically at that email's next signup (see 4.1.2). Either way, a share-invite email is sent via Resend with a link to the item (or to sign in, if the recipient has no account yet).
18. Every share, once created, shows a revoke control per link/grant. Revoking sets `revokedAt`; access checks always filter on `revokedAt IS NULL`.

### 4.5 Search and filtering
19.  Within a dashboar, a search/filter bar: name (text match), type (folder/file/data room), mimetype, size range, created/updated date range. Operates within the current node (data room, folder) subtree.

### 4.6 Account settings
20. Change password (requires current password) for accounts that have one.
21. Set password (no current-password check) for accounts created via Google only — offered as "add a password" rather than "change password."
22. Delete account (GDPR): cascades to every data room the user owns — all nodes, all `FileVersion` storage objects on Supabase, all shares and grants. Requires an explicit confirmation step naming the scope of what's being deleted, same pattern as node deletion.

## 5. Out of scope for this pass

- Real-time invalidation for active viewers when a node they're viewing is deleted (documented as a known gap, next request 404s cleanly).
- Editor role (schema supports it via `ShareGrant.role`, but only VIEWER is implemented).
- Resending/reminder emails for pending share invites.
