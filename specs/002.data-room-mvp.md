## §2 Domain model

### §2.1 Prisma schema (authoritative)

```prisma
enum NodeType     { DATAROOM FOLDER FILE }
enum ShareMode    { PUBLIC_LINK PERMISSIONED }
enum ShareRole    { VIEWER }

model User {
  id           String   @id @default(uuid())
  email        String   @unique          // stored lower-cased
  name         String
  passwordHash String?                    // null for Google-only accounts
  googleId     String?  @unique
  createdAt    DateTime @default(now())
  nodes        Node[]   @relation("NodeOwner")
  grants       ShareGrant[]
}

model Node {
  id         String   @id @default(uuid())
  parentId   String?                       // null iff type = DATAROOM
  type       NodeType
  name       String
  path       String                        // materialized path, see §2.2
  dataRoomId String                        // root node id; equals id for DATAROOM
  size       BigInt   @default(0)          // bytes
  itemCount  Int      @default(0)          // direct + nested descendants; FOLDER/DATAROOM only
  mimeType   String?                       // FILE only, mirrors latest version
  ownerId    String
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt
  deletedAt  DateTime?                     // reserved; MVP deletes are hard (§13.3)

  parent   Node?  @relation("NodeTree", fields: [parentId], references: [id], onDelete: Cascade)
  children Node[] @relation("NodeTree")
  owner    User   @relation("NodeOwner", fields: [ownerId], references: [id], onDelete: Cascade)
  versions FileVersion[]
  shares   Share[]

  @@unique([parentId, name])               // §6.1
  @@index([parentId, type, name])
  @@index([dataRoomId])
  @@index([path])
  @@index([ownerId, type])
}

model FileVersion {
  id            String   @id @default(uuid())
  nodeId        String
  storageKey    String   @unique           // uuid, never the filename
  size          BigInt
  mimeType      String
  checksum      String?                    // sha-256 hex, client-reported, advisory
  versionNumber Int
  createdAt     DateTime @default(now())
  createdById   String
  node Node @relation(fields: [nodeId], references: [id], onDelete: Cascade)
  @@unique([nodeId, versionNumber])
  @@index([nodeId, versionNumber(sort: Desc)])
}

model Share {
  id        String    @id @default(uuid())
  nodeId    String
  mode      ShareMode
  token     String?   @unique              // set iff mode = PUBLIC_LINK
  createdById String
  createdAt DateTime  @default(now())
  revokedAt DateTime?
  node   Node         @relation(fields: [nodeId], references: [id], onDelete: Cascade)
  grants ShareGrant[]
  logs   ShareAccessLog[]
  @@index([nodeId, revokedAt])
}

model ShareGrant {
  id         String    @id @default(uuid())
  shareId    String
  email      String                        // lower-cased
  userId     String?                       // null until an account with that email exists
  role       ShareRole @default(VIEWER)
  acceptedAt DateTime?
  createdAt  DateTime  @default(now())
  revokedAt  DateTime?
  share Share @relation(fields: [shareId], references: [id], onDelete: Cascade)
  user  User? @relation(fields: [userId], references: [id], onDelete: Cascade)
  @@unique([shareId, email])
  @@index([email, revokedAt])
  @@index([userId, revokedAt])
}

model ShareAccessLog {
  id           String   @id @default(uuid())
  shareId      String
  nodeId       String?                     // the node actually viewed within the share
  viewerUserId String?
  anonId       String?                     // cookie id for anonymous viewers
  viewedAt     DateTime @default(now())
  share Share @relation(fields: [shareId], references: [id], onDelete: Cascade)
  @@index([shareId, viewedAt])
}
```

### §2.2 Materialized path

`Node.path` is a **slash-delimited string of ancestor ids, inclusive of self,
with leading and trailing slash**:

- DATAROOM `R`: `/R/`
- FOLDER `F` under `R`: `/R/F/`
- FILE `X` under `F`: `/R/F/X/`

Rules:
1. Subtree of `N` (inclusive) = `path LIKE N.path || '%'`.
2. Ancestors of `N` (exclusive of self) = the ids parsed from `N.path`, minus
   the last. Ancestor lookups never require a recursive query.
3. `depth(N)` = number of ids in `path`. Max depth is **32** (§6.3).
4. On move, every node in the moved subtree has its `path` rewritten:
   `newPath = replace(path, oldPrefix, newPrefix)` in a single UPDATE.
5. `dataRoomId` is the first id in `path`, denormalized for cheap scoping.

### §2.3 Size and item-count invariants

- `FILE.size` = size of its **latest** `FileVersion`. Older versions do not count.
- `FILE.itemCount` = 0 and is never read.
- `FOLDER.size` / `DATAROOM.size` = Σ of `size` of all FILE descendants.
- `FOLDER.itemCount` / `DATAROOM.itemCount` = count of all descendants
  (folders **and** files, at any depth).
- Both are maintained **incrementally, in the same transaction as the write**,
  by applying a delta to every ancestor:
  `UPDATE "Node" SET size = size + $d, "itemCount" = "itemCount" + $c, "updatedAt" = now() WHERE id IN (ancestors)`.
- The same statement satisfies 001 §4.3 item 14 (parent `updatedAt` bumped on
  upload / move / rename / delete). **Rename** bumps ancestors with a zero delta.
- A maintenance function `recomputeRollups(nodeId)` exists and is used **only by
  tests** to assert the incremental path produced the same answer as a full
  recompute.

### §2.4 Domain objects (in `domain/`)

| Object | Responsibility |
|---|---|
| `NodeName` (VO) | trim, reject empty / `/` / `\0` / `.` / `..`, max 255 chars, NFC-normalize |
| `NodePath` (VO) | build, parse, prefix-test, depth, re-parent |
| `NodeEntity` | type invariants (DATAROOM ⇒ parentId null; FILE ⇒ no children) |
| `ConflictResolver` | given a sibling-name set and a desired name, produce the `(1)`-suffixed free name (§6.2) |
| `AccessDecision` | pure evaluation of §5.2 given (node path, viewer, owner, share set) |
| `RollupDelta` | pure computation of `{sizeDelta, countDelta}` for each mutation kind |

## §3 Authentication and session

### §3.1 Mechanism

- Session = **JWT in an httpOnly, SameSite=Lax, Secure (prod) cookie** named
  `dr_session`. Lifetime 7 days. No refresh token; re-login on expiry.
- Payload: `{ sub: userId, email, iat, exp }`. Signed HS256 with `JWT_SECRET`.
- There is **no self-serve email/password signup** (001 §2). Accounts come from
  (a) the seeded demo user, (b) Google OAuth first sign-in.

### §3.2 Endpoints

| Method | Path | Body | 200 response |
|---|---|---|---|
| POST | `/auth/login` | `{ email, password }` | `{ user }` + sets cookie |
| POST | `/auth/logout` | — | `{ ok: true }` + clears cookie |
| GET | `/auth/me` | — | `{ user }` or 401 |
| GET | `/auth/google` | — | 302 → Google consent |
| GET | `/auth/google/callback` | `?code` | 302 → `WEB_URL/` + sets cookie |

`user` = `{ id, email, name, hasPassword: boolean, hasGoogle: boolean }`.

### §3.3 Login rules

- Email compared case-insensitively (stored lower-cased).
- Password verified with bcrypt (cost 12).
- Wrong email and wrong password produce the **same** response:
  `401 { error: { code: "INVALID_CREDENTIALS" } }` — no user enumeration.
- An account with `passwordHash = null` attempting password login gets the same
  `INVALID_CREDENTIALS`, not "use Google".
- Rate limit: 10 failed attempts per email per 15 minutes → `429 RATE_LIMITED`.

### §3.4 Google OAuth

- Scopes `openid email profile`.
- Match order: `googleId` → else `email` (link Google to the existing account by
  setting `googleId`) → else create a new `User` with `passwordHash = null`.
- Google's email is trusted as verified.

### §3.5 First-visit grant linking (001 §4.1.2)

On **every** successful authentication (login, Google callback), inside one
transaction:

```
UPDATE "ShareGrant" SET "userId" = $userId
WHERE lower(email) = $userEmail AND "userId" IS NULL AND "revokedAt" IS NULL
```

This is idempotent and cheap, so it runs on every auth rather than on a
"first visit" flag. `acceptedAt` is set separately, the first time the user
actually opens the shared node (§8.6).

### §3.6 Seeded demo user

`prisma/seed.ts` upserts:
`email: demo@strongroom.test`, `name: "Demo User"`,
`password: demo-password-001` (bcrypt-hashed), and — only when the seed creates
the user fresh — one data room `Demo Data Room` containing one folder
`01 Corporate` and no files. Seeding is idempotent.

## §4 API conventions

### §4.1 Base and format

- Base URL `/api/v1`. JSON in, JSON out, UTF-8.
- `BigInt` fields (`size`) are serialized as **strings** in JSON.
- Dates are ISO-8601 UTC strings.
- All request bodies and query strings are validated by Zod schemas from
  `packages/contracts`; the same schemas type the web client.

### §4.2 Error envelope

Every non-2xx response body is:

```json
{ "error": { "code": "STRING_CODE", "message": "human readable", "details": { } } }
```

| Code | HTTP | Meaning |
|---|---|---|
| `VALIDATION_FAILED` | 400 | Zod rejection; `details.issues` |
| `INVALID_CREDENTIALS` | 401 | §3.3 |
| `UNAUTHENTICATED` | 401 | No/expired session where one is required |
| `FORBIDDEN` | 403 | Authenticated but access check failed (§5) |
| `NOT_FOUND` | 404 | Node/share does not exist **or** viewer may not see it (§5.4) |
| `NAME_CONFLICT` | 409 | §6.2; `details = { conflictingNodeId, conflictingNodeType, suggestedName }` |
| `INVALID_MOVE` | 409 | Move into self/descendant, or into a FILE, or depth > 32 |
| `UPLOAD_VERIFICATION_FAILED` | 409 | Storage object absent, or size/content-type mismatch (§7.4) |
| `PAYLOAD_TOO_LARGE` | 413 | Declared size > `MAX_FILE_BYTES` |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | mimeType not in the allow-list (§7.2) |
| `RATE_LIMITED` | 429 | §3.3 |
| `INTERNAL` | 500 | Unexpected |

`403` vs `404`: see §5.4.

### §4.3 Pagination

Cursor-based everywhere a list can grow:

- Request: `?limit=<1..100, default 50>&cursor=<opaque>`
- Response: `{ "items": [...], "nextCursor": "…" | null }`
- Sort is `?sort=name|size|updatedAt&dir=asc|desc`, default `name`/`asc`.
  Folders always sort before files regardless of sort key (design §2.1); this is
  implemented as a leading **type rank** term (`DATAROOM`/`FOLDER` = 0,
  `FILE` = 1).
- The full sort tuple is therefore `(typeRank, sortKey, id)`, and the cursor is
  base64url of all three fields from the last returned row. The query is the
  row-value comparison
  `WHERE (typeRank, sortKey, id) > (cursor.typeRank, cursor.sortKey, cursor.id)`,
  with the direction flipped for `dir=desc`. `id` is the tie-breaker that makes
  the tuple total, so a page boundary can never repeat or skip a row.
  **No OFFSET is used anywhere.**

### §4.4 Node representation

```ts
type NodeDto = {
  id: string; parentId: string | null;
  type: "DATAROOM" | "FOLDER" | "FILE";
  name: string;
  size: string;            // bytes, stringified BigInt
  itemCount: number;       // 0 for FILE
  mimeType: string | null;
  dataRoomId: string;
  ownerId: string;
  ownerName: string;       // "uploaded by" column, design §2.1
  createdAt: string; updatedAt: string;
  isShared: boolean;       // has ≥1 active Share directly on this node
  viewerRole: "OWNER" | "VIEWER";
}
```

`BreadcrumbDto = { id, name, type }[]`, root-first, **filtered to the segments
the viewer may see** (§5.5).

## §5 Access control

### §5.1 Principals

1. **Owner** — `Node.ownerId` of the node or of any ancestor.
2. **Grantee** — holds an active `ShareGrant` (`revokedAt IS NULL`, `userId = me`)
   on an active `Share` (`revokedAt IS NULL`) whose `Share.nodeId` is the node or
   an ancestor of it.
3. **Link viewer** — presents a token for an active `PUBLIC_LINK` `Share` whose
   node is the node or an ancestor of it. Anonymous or authenticated.

### §5.2 Decision rule (default-deny)

```
canRead(node, viewer) :=
     viewer.isOwnerOf(node.dataRoomId)
  OR ∃ share : share.revokedAt IS NULL
            AND node.path LIKE share.node.path || '%'
            AND (
                 (share.mode = PERMISSIONED AND ∃ grant ∈ share.grants :
                      grant.revokedAt IS NULL AND grant.userId = viewer.id)
              OR (share.mode = PUBLIC_LINK AND viewer.token = share.token)
            )

canWrite(node, viewer) := viewer.isOwnerOf(node.dataRoomId)
```

`ShareRole` is `VIEWER` only in this pass, so no grant ever confers write (001
§5). Write = create/rename/move/delete/upload/share/revoke.

### §5.3 Implementation shape

`canRead` is evaluated as **one query** (not N ancestor lookups): the candidate
share set for a viewer is
`SELECT s.id, n.path FROM "Share" s JOIN "Node" n ON n.id = s."nodeId" WHERE …viewer clause…`,
then the node's path is prefix-tested against those paths in the application
layer. For list endpoints the same set is turned into a SQL predicate
(`path LIKE ANY(...)`) so filtering happens in the database, not after fetch.

### §5.4 403 vs 404

- Viewer **cannot read** the node → `404 NOT_FOUND`. Existence is not leaked.
- Viewer **can read but not write** (grantee attempting a mutation) → `403 FORBIDDEN`.

### §5.5 Breadcrumb truncation

A grantee shared only `/R/F/G/` must not learn the names of `R` and `F`. The
breadcrumb returned starts at the **highest ancestor the viewer can read** — for
a grantee, the shared node itself; for the owner, the data room root.

### §5.6 Public-link scope

A public link on node `S` grants read of `S` and its whole subtree. Requests
carry the token as `?t=<token>` (or header `X-Share-Token`). A tokened request
that resolves to a node outside `S`'s subtree gets `404`.

## §6 Naming, conflicts, and structure

### §6.1 Uniqueness

`(parentId, name)` is unique **across all types** — a folder and a file cannot
share a name in one parent. Enforced by DB constraint and checked in the
application layer first so the user gets `NAME_CONFLICT`, not a 500.

001 §4.3a scopes conflict resolution to two FILE nodes. This spec extends the
**detection** to any type pair, but the three-way resolution dialog is offered
only when both incoming and existing are FILE. Otherwise only *keep both* /
*cancel* apply — a folder cannot become a version of a file. (§13.1)

### §6.2 Suffixing (keep-both)

Given desired `name` and the set of sibling names:
- Split into `stem` + `ext` (`ext` = last `.`-segment if the node is a FILE and
  the name has a dot after position 0; folders have no extension).
- If `stem` already ends with ` (k)` for integer k, that suffix is stripped first.
- Try `stem (1).ext`, `stem (2).ext`, … and return the first free one.
- Deterministic and pure — lives in `domain/ConflictResolver`.

### §6.3 Structural rules

- Depth ≤ 32 (`NodePath.depth`), enforced on create/move → `INVALID_MOVE`.
- A FILE may not be a parent → `INVALID_MOVE`.
- A node may not move into itself or a descendant → `INVALID_MOVE`.
- A DATAROOM may not be moved (it has no parent) → `INVALID_MOVE`.
- Name max 255 chars after trim; empty, `.`, `..`, and names containing `/` or
  NUL are rejected → `VALIDATION_FAILED`.

### §6.4 Conflict protocol (uniform across upload, rename, move)

Every conflict-capable request accepts an optional `onConflict` field:

```
onConflict?: "KEEP_BOTH" | "NEW_VERSION" | "REPLACE"
```

- **Omitted** and a conflict exists → `409 NAME_CONFLICT` with
  `details.suggestedName` (the §6.2 result) and `details.conflictingNodeId`.
  Nothing is written. The client shows the dialog and retries with a choice.
- **`KEEP_BOTH`** — the *moving/incoming* node takes the suffixed name.
  (001 §4.3a says for rename/move "the existing node (A) simply takes the
  suffixed name"; A *is* the node being renamed/moved, so this is the same rule
  stated from the other side.)
- **`NEW_VERSION`** — incoming content becomes a new `FileVersion` on the
  existing node B. For rename/move: A's **latest** version row is re-pointed to B
  with `versionNumber = B.maxVersion + 1`, A's older versions are deleted
  (rows + storage objects), then A is deleted. For upload: the uploaded object
  becomes B's next version.
- **`REPLACE`** — all of B's existing versions are deleted (rows + storage
  objects); the incoming content becomes B's `versionNumber = 1`. For rename/move,
  A is then deleted.
- `NEW_VERSION` / `REPLACE` on a non-FILE pair → `VALIDATION_FAILED`.
- Every version-history deletion goes through the same
  `StorageCleanup.deleteObjects(keys)` pass used by node deletion (001 §4.3a
  closing line) — invoked **after** the DB transaction commits (§10.2).

## §7 Uploads

### §7.1 Flow

```
1. POST /api/v1/uploads/init        → { uploadId, storageKey, signedUrl, expiresAt, conflict? }
2. Browser PUT file → signedUrl      (progress from XHR upload events)
3. POST /api/v1/uploads/{uploadId}/complete → NodeDto
```

`uploads/init` **does not** write a `Node`. It records a short-lived
`PendingUpload` row (`id, parentId, name, declaredSize, declaredMimeType,
storageKey, createdById, expiresAt`) so `complete` cannot be spoofed with
arbitrary parameters.

### §7.2 Limits and allow-list

- `MAX_FILE_BYTES` = 5 GiB (design §2.3 "max 5 GB per file"). Exceeded at init →
  `413 PAYLOAD_TOO_LARGE`.
- Allowed mime types: `application/pdf`, `image/png`, `image/jpeg`,
  `text/csv`, `text/plain`,
  `application/vnd.openxmlformats-officedocument.{spreadsheetml.sheet,wordprocessingml.document,presentationml.presentation}`,
  `application/vnd.ms-excel`, `application/msword`, `application/zip`.
  Anything else → `415 UNSUPPORTED_MEDIA_TYPE`.
- The signed URL is scoped to the single `storageKey`, pins `content-type` to the
  declared mime type, and expires in 15 minutes.
- The bucket independently enforces max size and the mime allow-list.

001 §2 pins the signed URL's content-type to `application/pdf`. This spec widens
it to the declared type from the allow-list, because 001 §4.5 requires mimetype
filtering across spreadsheets/images and the design shows XLS/CSV/DOCX/JPG in
every room. (§13.2)

### §7.3 Conflict at init

`init` reports `conflict: { conflictingNodeId, suggestedName }` **without
failing**, so the browser can raise the dialog before spending bandwidth. The
authoritative check still happens at `complete` (a sibling may have appeared in
between) — `complete` returns `409 NAME_CONFLICT` if `onConflict` is absent.

### §7.4 Verification at complete (001 §2, non-negotiable)

Before any DB write, the API calls Supabase Storage for the object's metadata and
requires:
- the object **exists**,
- `size === PendingUpload.declaredSize`,
- `contentType === PendingUpload.declaredMimeType`.

Any mismatch → `409 UPLOAD_VERIFICATION_FAILED`, the orphan object is deleted,
and the `PendingUpload` is consumed. The client's claim is never trusted.

### §7.5 Node creation on complete

In one transaction: create (or version) the `Node`, insert `FileVersion`
(`versionNumber = max+1`), set `Node.size`/`mimeType` from the new version, apply
the §2.3 rollup delta to all ancestors, delete the `PendingUpload`.

### §7.6 Download and preview

- `GET /api/v1/nodes/{id}/content?version=<n>` → `{ url, expiresAt, filename, mimeType }`
  where `url` is a 5-minute signed **download** URL with
  `content-disposition: inline` (preview) or `attachment` (`?download=1`).
- Access-checked by §5.2. For a tokened request, a `ShareAccessLog` row is written.
- The in-app PDF viewer fetches that URL directly; no proxying through the API.

```ts
ShareStateDto = {
  link: { shareId, token, url, createdAt } | null,
  grants: { id, email, name: string | null, role: "VIEWER",
            status: "ACCEPTED" | "PENDING", invitedAt, acceptedAt }[],
  inheritedFrom: { nodeId, name } | null   // design §5.2 "Access inherits from …"
}
```

- `POST …/shares/people` lower-cases and de-duplicates emails, skips emails that
  already hold an active grant on this share, creates `ShareGrant` rows (with
  `userId` resolved if an account exists), and sends one Resend invite per new
  grant (§9).
- Revoking is a soft revoke; access checks filter `revokedAt IS NULL` (001 §4.4.18).

### §8.4 Public link access (**public**, no session required)

| Method | Path | Response |
|---|---|---|
| GET | `/public/shares/{token}` | `{ node: NodeDto, breadcrumb, share: { mode, nodeId } }` + logs access |
| GET | `/public/shares/{token}/nodes/{id}` | same shape, scoped to the subtree (§5.6) |
| GET | `/public/shares/{token}/nodes/{id}/children` | paginated `NodeDto[]` |
| GET | `/public/shares/{token}/nodes/{id}/content` | signed URL, logs access |

Anonymous viewers get an `dr_anon` cookie (uuid) on first touch; it is written to
`ShareAccessLog.anonId`. Authenticated viewers log `viewerUserId` instead.
A revoked or unknown token → `404 NOT_FOUND` (design §6.2: "no longer available").

### §8.5 Search (001 §4.5)

`GET /nodes/{id}/search` — searches the **subtree of `{id}`**, which may be a
data room or a folder.

| Param | Type | Notes |
|---|---|---|
| `q` | string | case-insensitive substring on `name` |
| `type` | `FOLDER \| FILE \| DATAROOM`, repeatable | |
| `mimeType` | string, repeatable | exact match |
| `minSize` / `maxSize` | integer bytes | inclusive |
| `createdFrom` / `createdTo` | ISO date | inclusive |
| `updatedFrom` / `updatedTo` | ISO date | inclusive |
| `cursor` / `limit` / `sort` / `dir` | §4.3 | |

Response items are `NodeDto & { pathLabel: string }` where `pathLabel` is the
human folder trail (`"02 Financials / Audited Statements"`, design §8.2),
truncated per §5.5. Results are restricted by §5.2 like any list.

### §8.6 Account (001 §4.6)

| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/account/password` | `{ currentPassword?, newPassword }` | `204` |
| GET | `/account/delete-preview` | — | `{ dataRooms, documents, collaborators }` counts |
| DELETE | `/account` | `{ confirmEmail }` | `204` + clears cookie |

- `currentPassword` is **required** when `passwordHash != null` and verified;
  omitted/ignored when it is null ("add a password", design §9.2).
- `newPassword`: min 12 chars (design §9.1/§9.2), max 200.
- Account delete requires `confirmEmail` to equal the account email
  (case-insensitive) → else `VALIDATION_FAILED`. It cascades to every owned data
  room: nodes, versions, shares, grants (DB cascade) plus a storage-cleanup pass
  over every `FileVersion.storageKey` in those subtrees.
- `acceptedAt` on a `ShareGrant` is stamped the first time that grantee
  successfully reads the shared node.

## §9 Email (Resend)

- One template: **share invite**. Sent on grant creation only (001 §5: no
  resend/reminders in this pass).
- Subject: `{inviterName} shared "{nodeName}" with you`.
- Body links to `WEB_URL/n/{nodeId}` if the recipient has an account, else to
  `WEB_URL/login?next=/n/{nodeId}`.
- Sending is **best-effort and out-of-transaction**: a Resend failure is logged
  and does not roll back the grant or fail the request (the grant is the source
  of truth for access, the email is a notification).
- The port is `Mailer.sendShareInvite(input)`; the dev/test adapter is
  `InMemoryMailer`, asserted against in tests. No network in tests.

## §10 Storage cleanup and consistency

### §10.1 Port

```ts
interface FileStorage {
  createSignedUploadUrl(key, mimeType, maxBytes, ttlSec): Promise<{ url, expiresAt }>;
  createSignedDownloadUrl(key, opts): Promise<{ url, expiresAt }>;
  statObject(key): Promise<{ size: number; contentType: string } | null>;
  deleteObjects(keys: string[]): Promise<void>;
}
```
Adapters: `SupabaseFileStorage` (prod/dev), `InMemoryFileStorage` (tests).

### §10.2 Ordering

DB transaction commits **first**, storage deletion runs after. Rationale: an
orphaned storage object is a cost leak; a dangling `FileVersion` row pointing at
a deleted object is a broken product. Deletion is therefore always
DB-then-storage, never the reverse.

### §10.3 Orphan sweep

Keys whose storage deletion fails are appended to an `OrphanedObject` table
(`storageKey, failedAt, attempts`). A `sweepOrphans()` use case retries them; it
is exposed as a manual admin script, not a scheduled job (out of scope for MVP,
but the row must be written so nothing is lost silently).

### §10.4 Transactions

Every mutation in §6/§7 runs inside a single Prisma `$transaction` with
`isolationLevel: Serializable` for operations that touch ancestor rollups, so two
concurrent uploads into one folder cannot lose a size delta. Serialization
failures are retried up to 3 times before surfacing `500 INTERNAL`.

## §13 Amendments to spec 001

Recorded, not silent:

1. **§6.1** — 001 §4.3a scopes conflicts to two FILE nodes. Extended to detect
   conflicts across any type pair, because `(parentId, name)` uniqueness is
   enforced at the DB level for all types. Resolution options narrow to
   keep-both/cancel when the pair is not FILE+FILE.
2. **§7.2** — 001 §2 pins signed-upload content-type to `application/pdf`.
   Widened to an allow-list, because 001 §4.5 requires mimetype filtering and
   001 §4.3 shows non-PDF files. PDF remains the only type with an in-app viewer.
3. **§2.1 `deletedAt`** — 001 lists `deletedAt` on `Node` and the design shows a
   Trash with 30-day retention, but 001 has no restore flow and lists Trash
   nowhere in §4. MVP deletes are therefore **hard** deletes; the column is kept
   for a later soft-delete pass, and delete dialogs say "permanently deleted",
   not "moves to Trash".
4. **§2.2** — 001 §3 says `path` is `ltree`. Implemented as an indexed `text`
   materialized path instead: Prisma has no first-class `ltree` support (it would
   force every subtree query through `$queryRaw`, pushing SQL into layers that
   should not know it), and prefix matching on `text` with a btree index answers
   the same queries. Same semantics, one fewer extension, no raw-SQL leak.
5. **§10.3** — 001 requires "no orphaned objects". Added the `OrphanedObject`
   table + sweep so a failed storage delete is recorded rather than lost, which
   is the only way that requirement can actually hold.

## §14 Decisions this spec makes that 001 left open

| Decision | Choice | Why |
|---|---|---|
| Session mechanism | JWT in httpOnly cookie, 7d, no refresh | 001 names no mechanism; cookie avoids token storage in JS and works for the public-link routes too |
| Conflict protocol | 409 + retry with `onConflict` | Keeps the resolution decision on the client (where the dialog is) without a stateful "pending operation" server-side |
| Upload handshake | init → PUT → complete, with a `PendingUpload` row | 001 requires server-side verification before writing `FileVersion`; that needs a server-side record of what was promised |
| `itemCount` semantics | all descendants at any depth | Design shows "348 ITEMS · 12 FOLDERS" at room level — a whole-subtree count |
| 403 vs 404 | 404 when unreadable | Default-deny (001 §2) implies not leaking existence |
| Pagination cursor | `(type, sortKey, id)` tuple, base64url | 001 requires cursor-based, not offset; folders-first forces `type` into the tuple |
| Storage/DB ordering | DB commits first | §10.2 |
| Max depth | 32 | 001 says "any depth"; unbounded depth makes path rewriting unbounded — 32 is well past any real diligence tree |
| Password minimum | 12 chars | Taken from the design's own copy (§9.1) |

## §15 Open questions (not guessed at)

1. **Public-link `ShareAccessLog` granularity** — one row per node open is
   specified. Whether repeated opens within a session should be de-duplicated
   (e.g. one row per anon per node per hour) is undecided; MVP logs every open.
2. **Move of a shared node** — a `Share` follows the node (it is `nodeId`-based),
   so moving a shared folder into another room's tree would carry access across
   rooms. MVP forbids cross-data-room moves (`INVALID_MOVE`) rather than deciding
   the sharing semantics. Cross-room move is deferred.
3. **Google account with an email that already has a password account** — §3.4
   links them. Whether that should instead require a password confirmation step
   is a security decision left open; MVP links, matching 001's grant-linking
   posture.
