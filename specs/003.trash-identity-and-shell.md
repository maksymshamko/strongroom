# 003 — Trash, account identity, and the app shell

Builds on `specs/002.data-room-mvp.md`, which stays in force. This spec covers
three areas that 002 either deferred or left out:

1. **Account identity** — linking and unlinking Google, and keeping password
   state out of the general session payload.
2. **Trash** — 002 §13.3 made deletes hard and kept `Node.deletedAt` reserved.
   This spec spends that reservation: deletion becomes a move into a Trash node,
   with a TTL that eventually does the real deletion.
3. **App shell** — collapsible sidebar, user menu, theme (system/light/dark),
   mobile drawer, iconography, and breadcrumbs.

Section numbers are cited by tests. Where this spec changes a 002 decision, §8
records it.

---

## §1 Account identity

### §1.1 What leaves the session payload

002 §3.2 returned `UserDto = { id, email, name, hasPassword, hasGoogle }` from
every `/auth/*` call. `hasPassword` and `hasGoogle` are **removed** from that
shape — they describe the account's security posture, not the signed-in
identity, and they were rendered as a "Password: Set / Not set" row that told the
user nothing they could act on.

```ts
UserDto = { id, email, name }        // §1.1
```

They move to a dedicated, account-scoped endpoint (§1.2). The account settings
screen keeps its two password variants (002 §8.6, design §9.2) because it can
still ask for that state directly — it just isn't broadcast on every request.

### §1.2 `GET /account/security`

Requires a session; describes **only the caller's own** account.

```ts
AccountSecurityDto = {
  hasPassword: boolean;
  google: { connected: boolean; email: string | null };
}
```

### §1.3 Google sign-in matching order (restates 002 §3.4)

On a Google callback with no active session:

1. Match on `googleId`. Found → sign in.
2. Else match on the Google account's email. Found → **link**: set `googleId` on
   that user, then sign in.
3. Else create a new `User` with `passwordHash = null` and that `googleId`.

Unchanged from 002; restated because §1.4 adds a second entry point into the same
callback.

### §1.4 Linking Google to a signed-in account

| Method | Path | Behaviour |
|---|---|---|
| GET | `/account/google/link` | 302 → Google consent, with `state` marking this as a link flow |
| GET | `/auth/google/callback` | When a session is present, links rather than signs in |

Rules:
- The session's user gains the `googleId` from the profile.
- If that `googleId` already belongs to a **different** user →
  `409 IDENTITY_CONFLICT`. Google identities are not transferable.
- If the caller already has a different `googleId` linked → `409 IDENTITY_CONFLICT`.
  Unlink first.
- Linking does **not** require the Google email to match the account email — a
  person may sign in with a work Google account on a personal-email account.

### §1.5 Unlinking Google

`DELETE /account/google`

- If the account has **no password** (`passwordHash IS NULL`) → `409 PASSWORD_REQUIRED`
  with a message telling the user to set a password first. Unlinking otherwise
  would lock them out of their own account, which is exactly the failure mode
  001 asked this product to avoid.
- If no Google account is linked → `404 NOT_FOUND`.
- Otherwise `googleId` is set to null → `204`.

### §1.6 New error codes

| Code | HTTP | Meaning |
|---|---|---|
| `PASSWORD_REQUIRED` | 409 | The action would leave the account with no way to sign in |
| `IDENTITY_CONFLICT` | 409 | The external identity is already attached elsewhere |
| `RESTORE_TARGET_MISSING` | 409 | The folder an item was deleted from is gone or itself trashed (§2.6) |

## §2 Trash

### §2.1 Model

`NodeType` gains a fourth member: `TRASH`.

- Exactly **one TRASH node per user**, created lazily on that user's first
  delete and never itself deleted.
- It is a root: `parentId = null`, `path = /<trashId>/`, `dataRoomId = <its own id>`.
- Enforced by a unique index on `(ownerId)` where `type = 'TRASH'`.
- It never appears in `GET /data-rooms` (002 §8.1 lists `type = DATAROOM` only).

`Node` gains four columns. They answer two different questions, and separating
them is what makes the model unambiguous:

```
-- "is this node deleted?" — set on the deleted node AND every descendant
deletedAt        DateTime?

-- "is this an independently restorable Trash entry?" — set on the deleted node only
previousParentId String?     -- where it came from, for restore (§2.6)
previousName     String?     -- its name before any Trash de-duplication (§2.3)
deletedFromLabel String?     -- human trail, denormalized at delete time (§2.4)
```

`deletedAt` is deliberately **not** limited to the node the user clicked delete
on. A file inside a deleted folder *is* deleted, and asking whether it is should
not require knowing where its owner's Trash lives. Stamping the whole subtree
makes deletion a local, indexed fact:

- every read path filters `deletedAt IS NULL` instead of looking up the trash
  root and prefix-testing paths — one fewer query per request;
- the stamp costs nothing to write, because the delete already rewrites every
  descendant's `path` in a single UPDATE (002 §2.2 rule 4) and sets `deletedAt`
  in the same statement.

`previousParentId` is what distinguishes a restorable entry from a passenger.
Every node in a deleted subtree carries `deletedAt`; only the subtree's root
carries the restore fields.

### §2.2 Delete becomes a move

**Only the owner may delete.** 002 §5.2 already makes delete a write, and no
`Share` confers write, so a grantee or link viewer gets `403` / `404` exactly as
before. Trash does not soften that: an item can only ever reach the owner's
Trash, by the owner's own action.

`DELETE /nodes/{id}` (002 §8.1) no longer destroys rows. It:

1. Resolves (or lazily creates) the caller's TRASH node.
2. Re-parents the target under TRASH, rewriting the whole subtree's `path`
   exactly as a move does (002 §2.2 rule 4).
3. Stamps `deletedAt = now` across the **whole moved subtree**, and
   `previousParentId`, `previousName` and `deletedFromLabel` on the **target
   only** (§2.1). The subtree is restored or purged as a unit; the restore fields
   are what mark which node the unit is.
4. Applies the 002 §2.3 rollup: subtract the subtree's size and count from the
   old ancestor chain, add them to TRASH.
5. **Deletes** every `Share` and `ShareGrant` in the moved subtree — the rows are
   removed, not stamped with `revokedAt`.

Step 5 is stronger than 001 §4.3.13 requires: sharing does not survive deletion
even in a revoked form, so a trashed item is unreachable by a grantee or a public
link during the TTL window, and restoring it (§2.6) does **not** bring access
back. Re-sharing after a restore is a deliberate act the owner has to repeat.

Two consequences, accepted rather than hidden:

- A revoked public-link token is gone rather than dead, so re-sharing after a
  restore mints a **new** token. Anyone holding the old link sees "no longer
  available" permanently.
- `ShareAccessLog` rows cascade with their `Share` (002 §2.1), so the view
  history of a deleted item is destroyed with it. That is a real loss of audit
  trail; §9 records it as an open question rather than pretending it is free.

**No storage objects are deleted here.** That happens at purge (§2.7).

### §2.3 Name collisions inside Trash

Two files with the same name deleted from different folders would violate
`(parentId, name)` (002 §6.1). The move into Trash therefore applies the 002 §6.2
suffixing rule silently — no dialog, no `NAME_CONFLICT`. The user did not choose
this destination, so they are not asked to resolve it. `deletedFromLabel` is what
distinguishes the rows, not the suffix.

The suffix is an artifact of a database constraint, so it never reaches the user.
The pre-suffix name is kept in `previousName`, and that is what both the Trash
listing (§2.5) and a restore (§2.6) use — `Node.name` holds the de-duplicated
form purely to satisfy `(parentId, name)`.

Showing the original name is the clearer read precisely because `deletedFromLabel`
is already on the row: two entries called `Report.pdf` are told apart by where
they came from, which is what the user actually remembers, not by a `(1)` the
system invented. Two items deleted from the *same* folder under the same name
stay distinguishable only by their deletion time; that is accepted, and matches
how desktop trash behaves.

### §2.4 `deletedFromLabel`

The human folder trail the item was deleted from, resolved and stored **at delete
time**: `"Project Meridian / 02 Financials"`. It is denormalized deliberately —
the ancestors may themselves be trashed or purged later, and the label must
survive that. A data room deleted at its own root gets the label `"Data rooms"`.

### §2.5 Reading Trash

| Method | Path | Response |
|---|---|---|
| GET | `/trash` | `{ node: NodeDto \| null, items: TrashItemDto[], nextCursor: string \| null }` |

```ts
TrashItemDto = NodeDto & { deletedAt: string; deletedFromLabel: string }
```

`TrashItemDto.name` is the item's **original** name (`previousName`), not the
de-duplicated `Node.name` (§2.3). The internal form never leaves the server.

- Owner-only. There is no share path to a TRASH node.
- `node` is `null` before the user's first delete — the empty state, with no row
  written.
- Paginated per 002 §4.3, sorted by `deletedAt` descending by default.
- `GET /trash` also reports the TRASH node's `size` and `itemCount`, which are
  maintained incrementally like any other folder — that is the "hot path" for
  showing how much space deleted items still occupy.

### §2.6 Restore

`POST /trash/{nodeId}/restore` — owner-only, and only valid for a node that sits
directly in the caller's TRASH (a descendant that travelled inside a deleted
folder is not independently restorable; restore its ancestor instead).

It is the delete of §2.2 run backwards:

1. The destination is `previousParentId`. It must still exist **and be live** —
   if it was purged, or is itself sitting in Trash, the restore fails with
   `409 RESTORE_TARGET_MISSING`, naming the missing parent. Restoring the parent
   first then makes the child restorable, so a whole branch comes back by
   working outward-in. Nothing is ever silently relocated somewhere the user
   did not put it.
2. The node is re-parented to that destination under `previousName`, rewriting
   the subtree's paths.
3. `deletedAt` is cleared across the whole restored subtree, and
   `previousParentId`, `previousName` and `deletedFromLabel` are cleared on the
   target — the mirror of §2.2 step 3.
4. Rollups move back: subtract from TRASH, add to the destination's ancestor
   chain.
5. **Sharing is not restored.** §2.2 step 5 destroyed those rows; the item comes
   back private, and the owner re-shares it if they still want to.

If `previousName` is already taken in the destination, the standard 002 §6.4
conflict protocol applies unchanged — `409 NAME_CONFLICT` with a suggested name,
retried with `onConflict`. Restore is a move, so it uses the move's rules rather
than inventing its own.

### §2.7 Purging

- **TTL is 30 days** from `deletedAt` (design §6.1: "permanently removed after
  30 days").
- `purgeExpiredTrash()` hard-deletes every **subtree root** whose `deletedAt` is
  older than the TTL — that is, rows with both `deletedAt` past the cutoff and
  `previousParentId` set. Descendants carry `deletedAt` too (§2.1) but are never
  independent candidates; they go with their root, cascading versions, shares and grants, then purges
  every `FileVersion.storageKey` in those subtrees through the 002 §10.2
  DB-then-storage ordering.
- It runs **hourly inside the API process** and is also exposed as a script. It
  is idempotent and safe to run concurrently: each candidate is claimed by the
  delete itself, so a second runner finds nothing.
- Purging updates the TRASH node's rollups by the amount removed.

#### On-demand purging

Waiting 30 days is not the only way out. The owner may purge early:

| Method | Path | Behaviour |
|---|---|---|
| DELETE | `/trash/{nodeId}` | Permanently deletes one Trash entry and its subtree |
| DELETE | `/trash` | Empties the Trash entirely |

Both are owner-only, take the same code path as the TTL sweep — cascade, then
storage purge in the §10.2 order, then the TRASH rollup adjustment — and accept
only entries that sit directly in the caller's Trash (§2.6's rule about
passengers applies identically).

`DELETE /trash` on an empty or not-yet-created Trash is a no-op returning `204`,
not a `404`: emptying nothing is a successful outcome.

These are the only actions in the product with **no undo at all**, so the UI must
name exactly what is about to be destroyed — item counts and total size — and
must not present them as the default way to clear a row. Restore is the primary
action; permanent deletion is the deliberate one.

### §2.8 Everything else must ignore trashed nodes

A trashed node — and everything inside it — is invisible to every other read
path. Because §2.1 stamps the whole subtree, this is a plain `deletedAt IS NULL`
filter rather than a path comparison:

- `GET /nodes/{id}` and `/children` → `404` for any node with `deletedAt` set,
  which covers descendants of a deleted folder as well as the folder itself.
- Search (002 §8.5) excludes them the same way.
- Access checks (002 §5.2) deny it: its shares were revoked at §2.2 step 5, and
  its `dataRoomId` is now the trash root, which no one but the owner owns.

### §2.9 Delete preview copy

`GET /nodes/{id}/delete-preview` (002 §8.1) is unchanged in shape. The dialog's
copy changes from "permanently deleted" back to the design's original wording:
"moves to Trash and is permanently removed after 30 days".

## §3 Theme

### §3.1 Modes

Three: `system` (default), `light`, `dark`. The choice is stored in
`localStorage` under `dr.theme` — it is a device preference, not account state,
so it is not persisted server-side and needs no API.

### §3.2 Application

- `system` resolves through `prefers-color-scheme` and follows live changes.
- The resolved mode is applied as `data-theme="light" | "dark"` on `<html>`.
- A blocking inline script sets the attribute before first paint, so a dark-mode
  user never sees a white flash.

### §3.3 Dark palette

Roles are preserved, not inverted ad hoc: canvas stays behind surface, accent
stays action-only, danger stays reserved for destruction.

## §4 App shell

### §4.1 Collapsible sidebar (desktop ≥ 768px)

- Two states: expanded (200px, icon + label) and collapsed (56px, icon only).
- Collapsed items show their label in a tooltip on hover and on keyboard focus.
- The state persists in `localStorage` under `dr.sidebar`.
- A control at the sidebar's foot toggles it, with an `aria-expanded` label.

### §4.2 Icons

Lucide throughout, at 16px in navigation and rows, 14px inside buttons, always
`currentColor` and always paired with a text label or an `aria-label`. Icons
carry no information a sighted user could not also read.

| Concept | Icon |
|---|---|
| Data rooms | `layout-grid` |
| Shared with me | `users` |
| Trash | `trash-2` |
| Folder / open folder | `folder` / `folder-open` |
| File kinds | `file-text` (PDF), `sheet` (spreadsheet), `file` (other) |
| Upload | `upload` |
| New folder | `folder-plus` |
| Share | `share-2` |
| Rename | `pencil` |
| Move | `folder-input` |
| Download | `download` |
| Delete | `trash-2` |
| Search | `search` |
| Row menu | `more-horizontal` |
| Theme | `sun` / `moon` / `monitor` |
| Sign out | `log-out` |
| Settings | `settings` |
| Menu (mobile) | `menu` |
| Collapse / expand | `panel-left-close` / `panel-left-open` |

### §4.3 User menu

Sign-out moves off the sidebar surface and into a dropdown opened from the user
avatar. The menu contains, in order: the account's name and email (not
actionable), **Settings**, a **theme** segmented control (System / Light / Dark),
and **Sign out**.

### §4.4 Mobile (< 768px)

- The sidebar is replaced by a top header: burger (`menu`) on the left, the
  current screen title centred, and the user avatar on the right.
- The burger opens the navigation as a left drawer over a scrim; it closes on
  navigation, on scrim click, and on `Escape`.
- The avatar opens the same user menu as §4.3.
- Table columns degrade rather than scroll horizontally: Name and Modified are
  kept; Size and Uploaded-by are hidden below 768px, with size folded under the
  name.

### §4.5 Breadcrumbs

Breadcrumbs already exist (002 §8.1 returns the chain, and the browser renders
it). This section pins down what was left implicit:

- Shown on every node view — data room, folder, file preview, and the public
  link view — always root-first, and always truncated to what the viewer may see
  (002 §5.5).
- Every segment except the last is a link; the last is the current location and
  is not actionable.
- Above **four** segments the middle ones collapse into a single `…` item that
  opens a menu listing the hidden ancestors. First and last are never collapsed.
- On mobile only the parent and current segment are shown, prefixed by `…` when
  more exist.
- The Trash view shows a single non-navigable `Trash` crumb.

## §6 Data model delta

```prisma
enum NodeType { DATAROOM FOLDER FILE TRASH }

model Node {
  // …002 §2.1 unchanged…
  deletedAt        DateTime? // whole subtree (§2.1)
  previousParentId String?   // restorable-root marker (§2.1)
  previousName     String?
  deletedFromLabel String?

  @@index([deletedAt])
}
```

Plus a partial unique index, added by migration since Prisma cannot express it:

```sql
CREATE UNIQUE INDEX "Node_owner_trash_unique"
  ON "Node" ("ownerId") WHERE "type" = 'TRASH';
```

## §8 Decisions this spec makes

| Decision | Why |
|---|---|
| Trash is one node per user, not per data room | The user's answer; gives a single hot path for deleted size |
| `deletedFromLabel` is denormalized text | Its ancestors may be purged; a join could not answer it later |
| `deletedAt` on the whole subtree; restore fields on the target only | A file inside a deleted folder is deleted, and every read path should be able to say so without locating the owner's Trash. The stamp is written by the UPDATE that already rewrites descendant paths, so it is free; `previousParentId` separately marks which node is the restorable unit |
| Shares **destroyed** at delete, not revoked | The user's call: sharing should not survive deletion in any form, and must not silently come back on restore |
| Restore never relocates | Putting an item somewhere the user did not choose is worse than asking them to restore its parent first |
| `previousName` stored separately | Trash de-duplication mutates `name`; restore must return the name the user actually gave |
| Suffix silently inside Trash, and never show it | The user did not choose that destination, so it is neither their conflict to resolve nor theirs to look at; `deletedFromLabel` already disambiguates |
| Theme in `localStorage`, not on the account | A device preference; syncing it would need an API and would fight per-device choices |
| Hourly in-process purge | No scheduler exists in this stack; an interval plus a manual script is honest for MVP scale |

## §9 Open questions — resolved

All three were closed by the product owner during the 004 pass and are recorded
here rather than deleted, so the reasoning survives:

1. **Trash quota** — out of scope for the MVP. Trashed bytes count toward nothing
   and no storage limit exists yet.
2. **Access-log loss** — intended. Destroying a `Share` is meant to destroy its
   `ShareAccessLog` history with it; the log describes access through that share,
   so it does not outlive it.
3. **Purge cadence** — hourly and in-process is accepted for the MVP. Moving it
   to a job runner is a scaling concern, not a correctness one.
