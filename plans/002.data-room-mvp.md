## §2 Ports and adapters

Ports are defined in `application/ports/`, implemented in `infra/`, and bound at
the composition root by DI token (spec §1.3, §10.1).

| Port (application) | Adapters (infra) | Notes |
|---|---|---|
| `FileStorage` | `SupabaseFileStorage`, `InMemoryFileStorage` | spec §10.1 verbatim |
| `Mailer` | `ResendMailer`, `InMemoryMailer` | `sendShareInvite` only (§9) |
| `PasswordHasher` | `BcryptPasswordHasher` | keeps bcrypt out of `application/` |
| `TokenIssuer` | `JwtTokenIssuer` | keeps `jsonwebtoken` out of `application/` |
| `Clock` | `SystemClock`, `FixedClock` | lets expiry logic be tested without sleeping |
| `IdGenerator` | `UuidGenerator` | node ids are needed *before* insert to build `path` |
| `NodeRepository` | `PrismaNodeRepository` | tree reads/writes, rollups, cursor pagination |
| `ShareRepository` | `PrismaShareRepository` | active-share lookup for §5.3 |
| `UserRepository` | `PrismaUserRepository` | incl. grant linking (§3.5) |
| `UploadRepository` | `PrismaUploadRepository` | `PendingUpload` lifecycle |
| `UnitOfWork` | `PrismaUnitOfWork` | wraps `$transaction`, hides Prisma from use cases (§10.4) |

`UnitOfWork` is the decision that keeps §10.4 from leaking Prisma into
`application/`: a use case calls `uow.run(async (repos) => …)` and receives
transaction-scoped repository instances typed as the ports, never a
`Prisma.TransactionClient`.

Deferred storage deletion (§10.2) is expressed as the use case returning a list
of keys to purge; the application-layer `StorageCleanup` service runs them after
`uow.run` resolves and records failures via `OrphanRepository`. Ordering stays a
domain-visible rule rather than an accident of where `await` sits.

### §2.1 Ids before insert

`NodePath` needs the node's own id to build `path`, so ids are generated by
`IdGenerator` in the application layer and passed to the repository, rather than
relying on `@default(uuid())`. The Prisma default stays as a safety net.

## §3 Contract decisions the spec left open

These are decisions §14/§15 of the spec flagged as open, resolved here. Nothing
below contradicts a decision the spec already made.

1. **Cursor encoding** — base64url of `{"t":<typeRank>,"k":<sortKey>,"i":<id>}`.
   `typeRank` is `0` for DATAROOM/FOLDER, `1` for FILE, so folders-first
   (spec §4.3) is part of the tuple. Comparison is the SQL row-value form
   `(typeRank, sortKey, id) > (…)`, flipped for `dir=desc`.
2. **`ShareAccessLog` granularity** (spec §15.1) — MVP logs every open, as the
   spec states. No de-duplication is implemented; the open question stands.
3. **Cross-data-room move** (spec §15.2) — rejected with `INVALID_MOVE`, as the
   spec states. Enforced by comparing `dataRoomId` of source and destination.
4. **Google-account linking** (spec §15.3) — links by email, as the spec states.
   Google OAuth is wired but inert when `GOOGLE_CLIENT_ID` is unset; the login
   page hides the button in that case.
5. **Rate-limit storage** — the `LoginAttempt` table rather than in-process
   memory, so the limit survives restarts and holds across replicas.
6. **`itemCount` for a moved subtree** — the move applies
   `-(subtree.itemCount + 1)` to source ancestors and `+(subtree.itemCount + 1)`
   to destination ancestors; the `+1` is the moved node itself. Common ancestors
   receive both and net to zero, which is why the room total is unchanged by an
   internal move.
7. **`updatedAt` on rename** — Prisma's `@updatedAt` covers the renamed node;
   ancestors are bumped by the same rollup UPDATE with a zero delta, so one code
   path serves spec 001 §4.3.14 for all four mutation kinds.
8. **Public-route session handling** — the `AuthGuard` is opt-out via a
   `@Public()` decorator. Public share routes read an optional session (to log
   `viewerUserId` when present) but never require one.

## §5 Gate 4 — verification pass against the spec

Walked spec 002 section by section against §4 above.

**Every section appears in the traceability table.** §1.1, §3.6, §11.4, §11.5,
§12 and §15.1 appear with an explicit "no test, and why" rather than a test file.

**Every decision this plan makes was left open by the spec.** Checked
individually:

| Plan decision | Spec status | Verdict |
|---|---|---|
| Cursor encoding (§3.1) | §14 says "cursor-based, tuple `(type, sortKey, id)`, base64url" — the exact JSON shape is unstated | Plan detail. OK |
| Log every open (§3.2) | §15.1 explicitly says MVP logs every open | Plan follows spec. OK |
| Cross-room move rejected (§3.3) | §15.2 explicitly says MVP forbids it | Plan follows spec. OK |
| Google linking (§3.4) | §15.3 explicitly says MVP links | Plan follows spec. OK |
| `LoginAttempt` table (§3.5) | §3.3 requires the limit, names no storage | Plan detail. OK |
| Move `itemCount` arithmetic (§3.6) | §2.3 defines the invariant, not the arithmetic | Plan detail. OK |
| Rename bumps ancestors with a zero delta (§3.7) | §2.3 states this outright | Plan follows spec. OK |
| `@Public()` opt-out guard (§3.8) | §8.4 requires session-optional public routes | Plan detail. OK |
| `UnitOfWork` port (§2) | §10.4 requires transactions; §1.3 forbids Prisma in `application/` | Plan detail resolving a tension the spec created. OK |
| Ids generated before insert (§2.1) | §2.2 requires self-id in `path`; spec is silent on where ids come from | Plan detail. OK |

**Disagreements found: one.** The spec's §4.3 says the sort tuple is
`(type, sortKey, id)` while §14 writes it as `(type, sortKey, id)` in one place
and the cursor as `{sortKey, id}` in §4.3's prose. These describe the same tuple;
the prose in §4.3 was under-specified rather than wrong. Resolved **in the
spec** — §4.3 now states the cursor carries the type rank explicitly. No plan
adjustment was made to paper over it.

**No section of the spec is absent from the plan, and no plan step invents
behaviour the spec does not describe.** Gate 4 passes.
